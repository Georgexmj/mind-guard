# 系统架构设计文档

**项目：** MindGuard 社区老年认知障碍早筛与干预系统  
**当前口径：** 以 2026-04-29 代码实现为准

## 一、总体架构

当前系统采用“前后端分离 + 后端内置 AI 分析 + Celery 异步任务 + Docker Compose 基础设施”的架构。

```text
┌──────────────────────────────────────────────────────────┐
│ 用户交互层                                                │
│ Web 管理端 web-admin        微信小程序 miniprogram         │
│ 医生/管理员/家属/老人       老人评估与干预打卡              │
└───────────────────────────┬──────────────────────────────┘
                            │ HTTP(S) / JSON
┌───────────────────────────▼──────────────────────────────┐
│ Nginx 网关层                                               │
│ 静态资源服务、/api/v1 反向代理、HTTPS 证书、健康检查        │
└───────────────────────────┬──────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────┐
│ FastAPI 业务服务 backend                                  │
│ Auth / Users / Assessments / Questions / Dashboard         │
│ Interventions / Notifications / RAG / Communities          │
└───────────────┬───────────────────────────┬──────────────┘
                │                           │
        SQLAlchemy ORM                 Celery 任务
                │                           │
┌───────────────▼──────────────┐   ┌───────▼────────────────┐
│ 数据与对象存储                │   │ AI 与报告处理            │
│ MySQL / Redis / MinIO         │   │ rule/deep/hybrid 推理    │
│ InfluxDB / MongoDB            │   │ PDF、通知、提醒任务       │
└──────────────────────────────┘   └────────────────────────┘
```

## 二、模块职责

| 模块 | 目录/服务 | 主要职责 |
| --- | --- | --- |
| Web 管理端 | `web-admin/` | 管理看板、老人档案、评估详情、干预工单、题库、通知 |
| 小程序老人端 | `miniprogram/` | 登录、评估作答、语音/绘图任务、结果查看、干预打卡 |
| API 服务 | `backend/app/main.py` | 注册路由、CORS、健康检查 |
| 认证与权限 | `backend/app/core/`, `auth_service.py` | JWT、当前用户、角色权限 |
| 评估服务 | `assessment_service.py`, `routers/assessments.py` | 会话、题目、作答、完成、报告、趋势 |
| AI 服务 | `ai_service.py`, `deep_model_service.py` | 规则/深度/混合推理，生成风险等级和领域得分 |
| 干预服务 | `interventions.py`, `intervention_reco.py` | 推荐、计划、记录、依从性预警工单 |
| 通知服务 | `notification_service.py`, `wechat_service.py` | 站内通知、微信订阅消息配置预留 |
| RAG 服务 | `rag_service.py` | 知识库条目、索引、检索 |
| 异步任务 | `backend/app/tasks/` | AI 分析、提醒调度、Celery worker/beat |

## 三、核心业务流程

### 3.1 老人完成一次评估

```text
小程序/前端
  │
  ├─ POST /api/v1/assessments/sessions 创建会话
  ├─ GET  /api/v1/assessments/sessions/{id}/questions 获取题目
  ├─ POST /api/v1/assessments/sessions/{id}/answers 提交作答
  ├─ POST /api/v1/assessments/sessions/{id}/uploads/audio 上传语音
  ├─ POST /api/v1/assessments/sessions/{id}/complete 完成评估
  │
FastAPI 写入会话和作答
  │
Celery 异步分析
  │
AI 服务计算风险等级、领域分、解释字段
  │
写入 assessment_results 并生成通知
  │
前端查询 result / task 状态 / 家庭报告 / 医生 PDF
```

### 3.2 医生干预闭环

```text
评估结果
  │
GET /api/v1/interventions/recommendations/top5
  │
POST /api/v1/interventions/plans 或 /plans/from-top5
  │
老人每日 POST /api/v1/interventions/daily-checkin
  │
系统统计连续漏打卡与完成率
  │
生成 /adherence-tickets
  │
医生处理工单、分发提醒、安排复评
```

## 四、数据层设计

| 存储 | 当前作用 |
| --- | --- |
| MySQL | 用户、社区、评估、题库、结果、干预、通知、RAG 知识库 |
| Redis | Celery broker/result backend，后续可用于缓存与任务状态 |
| MinIO | 音频、报告、后续图像/附件存储 |
| InfluxDB | 行为时序数据预留 |
| MongoDB | 多模态原始特征 JSON 预留 |

本项目当前主要业务数据由 SQLAlchemy 自动建表；`infrastructure/mysql/init.sql` 是辅助初始化脚本，实际运行还会由 `backend/app/initial_data.py` 写入种子账号和题库。

## 五、AI 架构边界

当前工程没有独立 `ai-engine/` 服务。AI 分析位于后端：

| 文件 | 说明 |
| --- | --- |
| `backend/app/services/ai_service.py` | 评估分析入口，组织规则/深度/混合策略 |
| `backend/app/services/deep_model_service.py` | 加载 `models/deep_multimodal_fusion.pt` 并执行深度推理 |
| `backend/scripts/train_deep_multimodal.py` | 训练深度融合模型 |
| `data/` | 合成数据和训练清单 |

环境变量：

```env
AI_MODEL_STRATEGY=hybrid
DEEP_MODEL_CHECKPOINT=models/deep_multimodal_fusion.pt
DEEP_MODEL_DEVICE=cpu
DEEP_MODEL_ALLOW_RANDOM_INIT=false
DEEP_MODEL_BLEND_ALPHA=0.65
```

## 六、部署架构

| 服务 | 说明 |

## 七、安全设计

- 所有业务接口默认依赖 JWT 登录态。
- 角色权限在依赖层与路由层进行控制。
- 生产环境必须替换 `SECRET_KEY` 和所有默认数据库/对象存储密码。
- 微信小程序正式发布时必须使用 HTTPS 合法域名。
- 医疗相关结果仅作为筛查与随访辅助，不应在文案中承诺临床诊断。

## 八、后续扩展建议

| 方向 | 建议 |
| --- | --- |
| 独立 AI 服务 | 当推理耗时或模型体积增大后，再拆分 `ai-engine` 独立服务 |
| 多模态文件 | 增加独立 `/modality` 路由前，应先统一文件表与 MinIO 元数据 |
| 行为时序 | 接入 InfluxDB 前，先定义事件字典和采样频率 |
| 报告服务 | 若报告模板增多，可拆出 `/reports` 路由 |
| 生产可观测性 | 增加结构化日志、Prometheus 指标和告警 |
