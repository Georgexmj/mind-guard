## 一、总体架构设计

### 1.1 架构概览

系统采用**前后端分离 + AI引擎独立部署**的分层架构，共五个层次：

### 1.2 架构设计原则

| 原则 | 实现方式 |
|------|----------|
| **前后端分离** | REST API + JSON，前端独立部署 |
| **AI引擎解耦** | AI推理作为独立服务，通过内部HTTP调用，可独立扩展 |
| **异步处理** | AI分析通过Celery异步执行，避免HTTP超时（推理耗时10~30s） |
| **无状态服务** | JWT Token无状态鉴权，服务层无Session依赖，支持水平扩展 |
| **存储分类** | 结构化数据→MySQL，非结构化文件→MinIO，时序行为→InfluxDB |

## 二、各层技术选型详解

### 2.1 用户交互层

#### Web管理端（面向医生、管理员）

| 技术 | 版本 | 选型理由 |
|------|------|----------|
| React | 18.x | 生态成熟，Hooks模型适合复杂表单/数据流管理 |
| TypeScript | 5.x | 类型安全，提升大型代码库可维护性 |
| Ant Design | 5.x | 医疗/管理系统风格组件完整，表格/表单/布局开箱即用 |
| ECharts | 5.x | 雷达图、折线图、热力图支持完善，国内生态好 |
| Zustand | 4.x | 轻量状态管理，避免Redux的模板代码冗余 |
| React Query | 5.x | 服务端状态缓存与同步，减少重复请求 |
| Vite | 5.x | 开发服务器秒启动，HMR极快 |

#### 微信小程序（面向老人、家属）—— 基于UniApp开发

| 技术 | 版本 | 选型理由 |
|------|------|----------|
| UniApp | 3.x | 一套Vue代码编译为微信小程序，竞赛周期内快速交付 |
| Vue 3 | 3.x | Composition API，逻辑复用性强，团队学习成本低 |
| Pinia | 2.x | 轻量状态管理，替代Vuex，天然支持TypeScript |
| uni-ui | - | UniApp官方组件库，适配微信小程序样式规范 |
| wx.getRecorderManager | 原生API | 微信官方录音API，老人无需额外授权感知 |
| wx.getTextToSpeech | 原生API | 微信内置TTS，语音引导老年用户操作 |
| wx.chooseMedia | 原生API | 摄像头采集（人脸录入/拍照） |
| Canvas 2D | 原生API | 手写画布（时钟绘图测试） |
| wx.setStorageSync | 原生API | 本地缓存，离线答题数据暂存 |

**选用微信小程序而非原生App的核心理由：**
- 老年人微信使用率 > 85%，无需安装新App，扫码/搜索即用
- 家属直接通过微信转发小程序码给老人，引导门槛极低
- 微信已内置大字体/高对比度无障碍支持，天然适配老年群体
- 订阅消息可替代推送通知，合规且体验一致

**微信小程序通知限制说明：**
小程序无法主动推送通知，改用**微信订阅消息**方案：
- 老人首次评估时授权订阅"评估结果通知"和"健康提醒"
- 高危预警触发时，后端调用微信订阅消息API推送给老人和家属

**老年友好界面核心设计规范：**
- 最小字体：32rpx（约等效16px，使用`uni.getSystemInfo`读取系统字体缩放）
- 触控区域：最小88rpx × 88rpx（约44×44pt）
- 颜色对比度：≥7:1（WCAG AAA级）
- 交互层级：最深2层，无复杂菜单
- 每屏一个主任务原则
- 关键操作加`long-press`长按2秒确认（防误触）
- 完成操作即调用`wx.vibrateShort()`+TTS确认音双反馈

### 2.2 API网关层

```
Nginx 1.25
├── SSL/TLS 终止（HTTPS）
├── 静态资源服务（Web前端打包产物）
├── 反向代理 → FastAPI（/api/v1/*）
├── 反向代理 → AI引擎（/internal/ai/*，仅内网可达）
├── 请求限流（令牌桶：100 req/s/IP）
└── Gzip 压缩响应
```

JWT鉴权方案：
- Access Token：有效期2小时（HS256签名）
- Refresh Token：有效期30天（存储于Redis白名单）
- Token刷新：静默刷新，用户无感知

RBAC权限模型：
```
角色（Role）→ 权限集合（Permissions）
elder:      read:own_data, write:assessment_answer
family:     read:elder_data, write:intervention_feedback
doctor:     read:community_data, write:intervention_plan, write:elder_note
admin:      read:all, write:all, manage:system
```

### 2.3 业务服务层

| 服务 | 路由前缀 | 主要职责 |
|------|----------|----------|
| 用户服务 | `/api/v1/users`, `/api/v1/auth` | 注册登录、权限管理、关系绑定 |
| 筛查服务 | `/api/v1/assessments` | 评估会话管理、自适应题目分发、作答收集 |
| 多模态服务 | `/api/v1/modality` | 音视频上传、手写数据接收、特征提取调度 |
| 干预服务 | `/api/v1/interventions` | 推荐方案生成、计划管理、执行记录 |
| 报告服务 | `/api/v1/reports` | 评估报告查询、PDF导出、趋势数据聚合 |
| 社区服务 | `/api/v1/communities` | 社区看板数据、GIS分布、预警管理 |

**异步任务设计（Celery + Redis）：**

```
HTTP请求触发评估完成
    → 立即返回 202 Accepted + taskId
    → Celery任务队列
        ├── Task 1: 多模态特征提取（10~20s）
        ├── Task 2: AI模型推理（5~15s）
        └── Task 3: 报告生成 + 通知推送（2~5s）
客户端轮询 /assessments/{id}/status 查询进度
    → 完成后返回 200 + 完整结果
```

### 2.4 AI引擎层

详见 [AI算法设计文档](../ai/algorithm_design.md)

**服务接口：**

| 接口 | 说明 | 预估耗时 |
|------|------|----------|
| `POST /internal/ai/analyze` | 完整多模态分析 | 15~30s |
| `POST /internal/ai/asr` | 语音识别（FunASR） | 3~8s |
| `POST /internal/ai/face` | 面部表情分析 | 1~3s |
| `POST /internal/ai/handwriting` | 手写笔迹分析 | 1~2s |
| `POST /internal/ai/predict-risk` | 纵向风险预测 | 0.5~1s |
| `POST /internal/ai/recommend` | 干预方案推荐 | 0.5~1s |

**模型部署策略：**
- 推理框架：ONNX Runtime（PyTorch模型导出ONNX格式，推理速度提升2~5倍）
- 模型加载：服务启动时预加载至内存，避免推理时磁盘IO
- 版本管理：MLflow跟踪实验，模型文件存储于MinIO

### 2.5 数据存储层

| 存储 | 用途 | 数据规模估算 |
|------|------|------------|
| **MySQL 8.0** | 用户信息、评估记录、干预计划等结构化业务数据 | 主要业务表，万级行 |
| **Redis 7.0** | JWT黑名单、会话缓存、Celery任务队列、评估进度状态 | 内存级，KB~MB |
| **MinIO** | 音频文件、视频片段、手写图像、生成的PDF报告 | 每次评估约50~200MB |
| **InfluxDB 2.0** | 触屏行为时序数据（毫秒级精度，高频写入） | 每次评估约10万条点 |
| **MongoDB 6.0** | 多模态原始特征JSON、AI分析中间结果 | Schema灵活，文档级 |

## 四、部署架构

### 4.1 Docker Compose 开发/演示环境

```yaml
服务清单：
  nginx:         反向代理（主机端口30000，生产常见80/443）
  backend:       FastAPI业务服务（主机30001，容器8000）
  ai-engine:     AI推理服务（端口8001，仅内网）
  celery-worker: 异步任务消费者
  mysql:         数据库（主机30002，容器3306）
  redis:         缓存与消息队列（主机30003，容器6379）
  minio:         对象存储（主机30004/30005控制台，容器9000/9001）
  influxdb:      时序数据库（主机30006，容器8086）
  mongodb:       文档数据库（主机30007，容器27017）
```

### 4.2 生产环境扩展方案

```
负载均衡（Nginx）
    ├── Backend × N（水平扩展，无状态）
    ├── Celery Worker × M（按任务类型分队列扩展）
    └── AI Engine × K（GPU节点，推理密集型）

数据库高可用：
    MySQL → 主从复制 + 读写分离
    Redis → Sentinel 主从切换
    MinIO → 分布式模式（多节点）
```

## 五、安全设计

### 5.1 数据安全
- 用户手机号：AES-256加密存储
- 人脸特征向量：加密存储，不存储原始照片
- 医疗数据传输：全程HTTPS，禁止明文
- 音视频文件：MinIO存储，预签名URL访问（URL有效期15分钟）

### 5.2 隐私保护
- 老年用户数据访问：严格的RBAC控制（家属仅见绑定老人数据）
- 数据匿名化：研究/统计用途数据自动脱敏（去除姓名、手机号）
- 数据删除权：用户可申请删除个人数据（软删除 + 定期清理）

### 5.3 接口安全
- 所有API需携带有效JWT Token
- 内部AI引擎服务不暴露公网（仅Docker内网可达）
- 上传文件类型白名单（音频/图像/视频），大小限制200MB
- SQL注入防护：ORM参数化查询（SQLAlchemy）

## 六、性能设计

| 指标 | 目标值 | 实现手段 |
|------|--------|----------|
| API响应时间（P95） | ≤500ms | Redis缓存热点数据，数据库索引优化 |

| 文件上传速度 | ≥10MB/s | MinIO分片上传 |
| 移动App冷启动 | ≤3s | Flutter AOT编译 + 懒加载 |
